# 小说分解多轮补漏设计

## 目标

小说分解第一轮必须遍历全部分段。普通解析、格式、时间线、字段缺失、网络波动、限流或服务端临时错误造成的失败，不得结束任务；系统应自动开启下一轮，仅重跑失败分段，直到全部成功。只有明确的渠道级永久故障才停止。

## 根因

当前执行器在单分段局部重试耗尽后把分段标记为“失败”。虽然同一轮会继续后续分段，但当所有待处理分段耗尽时，任务立即进入最终失败状态，没有把普通失败重新排入下一轮。

实际错误样本还显示，模型经常把信息可见性写进 `内容` 文本，例如“事实 / 谁知道：A / 谁不知道：B / 否”，却没有输出结构化 `信息可见性` 字段。重复发送完全相同的请求容易再次得到同类错误，因此后续尝试必须携带上一次校验错误作为局部纠错要求。

## 执行模型

1. 第一轮处理所有“待处理”分段，成功项落盘，失败项记录最近错误并继续后续分段。
2. 一轮结束后，如果存在普通失败项：
   - 轮次加一；
   - 只把普通失败项重新排为“待处理”；
   - 保留成功分段，不重复请求；
   - 下一轮请求携带该分段上一次错误，要求 AI 只纠正对应结构问题。
3. 重复补漏，不设置最大轮数。轮次之间增加有上限的退避等待，避免持续格式失败时高速请求。
4. 所有分段成功后，任务才进入 `completed`。
5. 用户暂停或取消仍立即中断，并保留已完成进度。

## 渠道故障判定

以下错误视为不可通过内容重写解决的渠道级故障，立即停止任务并显示渠道、模型与错误：

- HTTP 401：密钥无效或未认证；
- HTTP 403：无权限、余额或计费权限不足；
- HTTP 404：接口、模型或请求资源不存在；
- 明确的无效 API 地址、无效模型、模型不存在；
- 明确的余额不足、计费未开通、配额永久耗尽。

以下错误不是渠道永久故障，继续进入后续轮次：

- HTTP 408、409、425、429、5xx；
- timeout、网络断开、代理波动、流式截断；
- `<结果>`/JSON 解析失败；
- 信息可见性、时间线、组号、关键事件等结构校验失败。

## 状态与进度

- 任务保存当前补漏轮次，缺省为第 1 轮。
- 进度提示包含“第 N 轮”“本轮待处理数”“当前剩余失败数”。
- 普通失败在轮次切换时属于“等待补漏”，不作为最终人工校对状态。
- 渠道故障保留失败分段和渠道错误，状态进入 `failed`。
- 执行百分比按当前已成功分段计算；轮次完成但仍需补漏时不得显示任务已完成。

## 局部纠错提示

分段再次请求时，在原任务上下文之外追加：

- 上一次失败原因；
- 必须重新输出完整分段结构，而不是只返回修补片段；
- 针对信息可见性错误，明确要求将 `谁知道`、`谁不知道`、`是否仅读者视角可见` 写入结构字段，不能拼进 `内容`；
- 针对时间错误，要求重新核对分段和关键事件的起止顺序。

## 测试

- 第一轮某段连续失败，后续分段仍成功执行。
- 第一轮结束后自动进入第二轮，只重跑失败段。
- 第二轮成功后任务完成，成功段不重复请求。
- 连续多轮普通格式错误不会进入最终失败。
- 401、403、404、无效模型或余额错误立即停止，不进入下一轮。
- 429、超时、5xx 和解析校验错误进入下一轮。
- 第二轮请求包含上一轮错误形成的局部纠错提示。
