# 多能力体系与离场 NPC 成长设计

## 目标

在保持旧存档、现有战斗计算和单体系 DIY 配置兼容的前提下，实现以下能力：

1. DIY 境界支持多个独立能力体系，每个角色可拥有一个主体系和若干副体系。
2. 不同体系通过共通战力档位换算，但保留各自的能力边界、资源类型和突破路线。
3. 离场 NPC 的后台行动在明确成功结算后，可以安全同步其正式档案中的境界与装备。
4. 世界演化不能凭职业、身份、时间经过或模糊叙述自动为 NPC 升级或生成装备。

## 非目标

- 不用多体系数据完全替换现有 `境界` 与 `境界层级` 字段。
- 不在本次改动中重写整个战斗系统。
- 不允许所有副体系档位直接相加形成无上限战力膨胀。
- 不允许世界演化任意写入 `社交[]` 的其他敏感字段。
- 不批量重写已有存档。

## 方案选择

采用兼容扩展方案：保留现有单一境界字段作为显示与综合数值真值，同时增加结构化多体系数据。

没有采用纯提示词方案，因为它无法稳定校验体系换算、旧存档兼容和 NPC 档案落盘。没有采用完全替换旧境界字段的方案，因为它会扩大到战斗、角色展示、存档迁移和大量既有提示词，风险与本次目标不匹配。

## 多能力体系数据模型

### DIY 配置

现有 `RealmDiyDraft.rows` 保留作为旧格式输入。新格式增加 `systems`：

```ts
interface RealmDiySystem {
    id: string;
    name: string;
    description: string;
    energyType: string;
    role: 'primary_or_secondary' | 'primary_only' | 'secondary_only';
    rows: RealmDiyRow[];
}

interface RealmDiyDraft {
    systems?: RealmDiySystem[];
    rows?: RealmDiyRow[];
    updatedAt?: number;
}
```

`RealmDiyRow.level` 继续表示共通战力档位。每个体系拥有自己的境界名称、能力定位、突破条件、参数与描述，但相同 `level` 表示大致处于同一综合实力档位。

旧草稿只有 `rows` 时，规范化逻辑自动生成一个名为“默认体系”的主体系候选，不修改原始存档内容。

### 角色与 NPC 能力状态

新增可选结构：

```ts
interface AbilitySystemProgress {
    systemId?: string;
    systemName: string;
    realmName: string;
    systemLevel: number;
    powerLevel: number;
}

interface CharacterAbilitySystems {
    primary: AbilitySystemProgress;
    secondary: AbilitySystemProgress[];
}
```

该结构可存在于玩家角色和 `社交[]` NPC 档案中。为保持兼容：

- `境界` 默认显示主体系的 `realmName`。
- `境界层级` 保存计算后的综合战力档位。
- 旧角色没有 `能力体系` 时，运行时把现有 `境界/境界层级` 视作单主体系，不强制写回。
- 新数据写入时同步维护旧字段，避免现有战斗、属性预算、显示和提示词失去数值来源。

### 综合战力档位

综合档位以主体系为基准，副体系只提供有限协同：

```ts
effectivePowerLevel = primary.powerLevel + synergyBonus
```

`synergyBonus` 取所有副体系中最高的一项，按主副档位差计算，并设置较低上限。第一版规则为：

- 没有副体系：加成 0。
- 副体系低于主体系 4 档以上：加成 0。
- 副体系低于主体系 1 至 3 档：加成 1。
- 副体系与主体系同档或更高：加成 2。
- 综合档位至少为 1，最高不超过当前境界母板支持的最高档位。

副体系的主要价值是扩展术法、治疗、感知、抗性、克制和剧情解法，而不是线性叠加数值。

## DIY 界面与提示词

DIY 境界编辑器增加体系列表，并允许：

- 新增、删除和重命名体系。
- 设置体系说明、能量类型和主副体系限制。
- 在每个体系内独立编辑境界行。
- 展示每个境界对应的共通战力档位。

至少保留一个体系。删除当前体系前必须保证仍有其他体系；空名称在规范化时使用稳定兜底名称。

生成的手动境界提示词包含：

1. 共通战力档位说明。
2. 每套体系的独立映射表。
3. 主体系与副体系规则。
4. 同档不等于能力相同的约束。
5. 旧式 `【境界映射母板】`，用于现有单值解析器和展示逻辑兼容。

兼容母板默认采用第一套允许作为主体系的体系；如果草稿把全部体系设为仅副体系，归一化会把第一套提升为可作为主体系或副体系。

## 离场 NPC 演化模型

### 后台跟踪对象

`世界.活跃NPC列表[i]` 增加可选的正式档案关联和结算候选：

```ts
interface ActiveNpcSettlement {
    status: 'pending' | 'success' | 'failed' | 'interrupted';
    reason: string;
    realmChange?: {
        systemId?: string;
        systemName: string;
        fromRealm: string;
        toRealm: string;
        systemLevel: number;
        powerLevel: number;
    };
    equipmentChanges?: Array<{
        action: 'gain' | 'equip' | 'unequip' | 'lose' | 'damage';
        itemName: string;
        source: string;
        slot?: string;
        description?: string;
    }>;
}
```

活跃 NPC 同时增加可选 `npcId`。正式档案匹配规则为：

1. 优先使用 `npcId` 匹配 `社交[].id`。
2. ID 未命中时使用规范化姓名作唯一兜底匹配。
3. 姓名必须唯一命中；零命中或多命中均拒绝落盘。

能力体系匹配同样采用稳定标识优先：优先使用 `systemId`；旧结算缺少 ID 时，才允许按唯一 `systemName` 兜底；名称零命中或多命中均拒绝落盘。

### 结算门槛

只有全部满足以下条件，才生成 NPC 档案同步命令：

- 后台行动已到结算时间或被本轮明确结算。
- `settlement.status` 为 `success`。
- 成功原因具体且能承接当前行动。
- NPC 能唯一匹配现有正式档案。
- 境界变化同时提供体系、旧境界、新境界、体系层级和共通档位。
- `fromRealm` 与正式档案当前境界一致，或与对应能力体系当前境界一致。
- 新档位不低于旧档位；单次跨越超过一个大阶段时必须在原因中存在明确重大机缘、传承或长期积累说明，否则拒绝。
- 装备变化提供具体物品名和来源；穿戴与卸下操作必须提供合法槽位。

`pending`、`failed`、`interrupted`、来源不明、重名歧义和状态冲突只保留后台世界结果，不修改正式 NPC 档案。

### 安全落盘桥接

世界演化模型仍主要输出 `世界.*` 与 `环境.*` 命令。新增一个本地、可测试的 NPC 结算桥接器：

1. 从规范化后的活跃 NPC 结算数据读取候选。
2. 对照本轮执行前的 `社交[]` 状态验证匹配和前置条件。
3. 只生成白名单中的最小 `社交[i]` 命令。
4. 交给现有响应命令处理器应用。

境界白名单字段包括：

- `社交[i].能力体系`
- `社交[i].境界`
- `社交[i].境界层级`
- 必要的结算记忆

装备白名单字段包括：

- `社交[i].当前装备.<槽位>`
- `社交[i].背包`
- 对已有明确物品的损毁或失去结果
- 必要的结算记忆

不得生成整对象覆盖、删除 NPC、修改关系、生死、身体或其他不相关字段的命令。

### 装备一致性

- `gain`：把有明确来源的物品合并加入 NPC 背包，不自动穿戴。
- `equip`：物品必须已经在背包中，或同一结算同时存在合法 `gain`；同轮 gain 会先结算，因此不依赖数组顺序。穿戴后从背包扣除该物品，避免装备与背包重复。
- `unequip`：清空指定槽位，并把原装备合并放回背包。
- `lose`：只能移除当前装备或背包中真实存在的同名物品。
- `damage`：只能作用于当前装备或背包中真实存在的同名物品；优先更新已有物品描述/状态，不凭空创建损坏物。

第一版不设计复杂物品 ID 合并和堆叠算法；沿用现有 NPC 背包、装备规范化与命令处理能力，桥接器只负责产生最小、合法的变化。

## 数据流

### 开局 DIY

1. 用户编辑多个体系。
2. 规范化草稿并迁移旧 `rows`。
3. 生成多体系提示词和兼容母板。
4. 开局生成及后续提示词读取体系换算规则。
5. 新角色按主体系和可选副体系建立能力状态，同时同步旧境界字段。

### 世界演化

1. 世界演化读取正式 NPC 摘要、活跃 NPC 行动和当前时间。
2. 模型推进后台行动并写出结构化结算状态。
3. 现有世界命令先经过路径白名单规范化。
4. NPC 结算桥接器读取成功结算候选并校验正式档案。
5. 合法候选转换为最小 `社交[i]` 命令。
6. 世界命令与 NPC 同步命令分别应用。
7. 无论是否落盘，世界演化摘要都必须与实际执行结果一致。

## 错误处理

- 旧草稿迁移失败时回退为默认单体系，不阻止开局。
- 多体系全部为空时使用现有默认境界草稿。
- 兼容母板无法选出主体系时使用第一套非空体系。
- NPC 结算验证失败时跳过正式档案命令，并保留可诊断的拒绝原因，不抛出导致整轮世界演化失败的异常。
- 单个装备变化非法时只拒绝该装备变化；境界变化可独立通过，反之亦然。
- 同一 NPC 同轮出现多个互相冲突的成功结算时全部拒绝，等待下一轮重新审计。

## 测试策略

### 多体系

- 旧 `rows` 草稿迁移为一个默认体系。
- 多体系规范化保留体系信息和独立境界行。
- 兼容母板选择第一套可作为主体系的体系。
- 相同档位的不同体系生成不同境界文案。
- 主体系单修综合档位不变。
- 副体系较弱、接近和同档时分别得到 0、1、2 的有限加成。
- 综合档位不会超过母板最高档位。
- 旧角色没有能力体系时仍按旧境界字段运行。

### NPC 后台结算

- 通过 `npcId` 唯一匹配 NPC。
- 无 ID 时通过唯一姓名匹配。
- 重名时拒绝落盘。
- 成功突破同步能力体系、境界和境界层级。
- 待定、失败或打断不修改正式档案。
- 旧境界不匹配时拒绝突破。
- 装备来源缺失时拒绝变化。
- 获得后穿戴同一物品可以在同轮合法完成。
- 不存在的装备不能丢失或损坏。
- 非白名单字段无法由桥接器生成。
- 某个非法装备变化不会阻止同轮合法境界变化。

### 回归

- 现有境界体系测试继续通过。
- 现有世界演化命令路径白名单测试继续通过。
- 现有 NPC 状态规范化与命令处理测试继续通过。
- TypeScript 类型检查、相关 Vitest 测试和生产构建通过。
- DIY UI 在暗色和日间主题下均可读，桌面与移动端至少完成基础交互检查。

## 完成标准

- 用户可以在 DIY 境界中建立至少两套体系，并分别维护境界。
- 生成提示词能明确表达“武者第二境与道士第一境同档但能力不同”。
- 玩家和 NPC 能记录主体系与副体系，同时旧境界字段继续可用。
- 离场 NPC 只有在成功结算且因果完整时才更新境界或装备。
- 非法、模糊和冲突结算不会污染正式 NPC 档案。
- 不部署；仅完成本地测试、构建和 UI 验证。
